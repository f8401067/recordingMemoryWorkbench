## 相邻录音（间隔 ≤5 分钟）真合并成一条

用户选择「真合并成一条记录」+「整组合并生成一份纪要」，音频不合并（仍分条保留）。

- 新服务 `server-py/app/services/merge.py`：
  - `find_merge_partner(id, window_ms)`：同用户、终态（ready/failed）、按 `_end_ms` 排序后相邻两条间隔 ≤ window → 返回 (保留=较早那条, 吸收=较晚那条)。
  - `merge_recordings(keep, drop)`：把 drop 的 chunks **整行改挂**到 keep（`UPDATE chunks SET recording_id/seq/path/start_offset/segments`），
    新 seq = keep 条数 + i，新 offset = keep 末尾时长 + 原 offset，段级 startMs/endMs 整体平移 delta；
    文件用 `shutil.move` 搬到 `uploads/<keep>/m{seq:05d}{ext}`；删 keep 的旧 summaries 并置 `summary_status='none'`；
    `DELETE recordings`（summaries 外键 CASCADE，devices.open_recording_id SET NULL）；`emit_recording(drop,'merged',{id:keep})` 让打开的详情页自动跳过去。
  - `reconcile_after_finalize(id, depth=3)` 链式合并。
- 触发：`services/transcribe.py::finalize_recording(recording_id, allow_merge=True)` 在 status=ready 后调 reconcile；
  若本条被吸收（`merged_id != id`）就直接 return，由主记录的 `finalize_recording(keep, allow_merge=False)` 统一走自动纪要。
- 迁移 `0004_merged_count`：`recordings.merged_count INTEGER DEFAULT 0`（=被吸收的条数，原始条数 = merged_count + 1）。
- 接口：`POST /api/recordings/merge`（body `{minutes:5}`，循环扫描直到没有可合并对，返回 `{merged, minutes}`）；
  `recording_card()` 增加 `mergedCount`。
- 前端：Recording type 加 `mergedCount`；`RecordingCard` 显示 chip「合并 N 段」（N = mergedCount+1，hover 说明音频仍分条）；
  详情页 SSE 收到 `merged` 事件就 `navigate` 到保留的那条。
- **坑**：`recordings` 表没有 `updated_at` 列（只有 `created_at`），合并时的 UPDATE 写 `updated_at` 会直接 500（异常处理器转成 db_unavailable）。
- 执行结果：合并前先 `pg_dump` 备份到 `data/backups/recall_20261031_before_merge.sql`；
  29 条 → 16 条（合并 13 次），102 个分片一个没丢、磁盘文件全部在位（缺文件检查通过），
  时间轴 `min(start_offset)=0 / max(end)=duration_ms` 连续、segments 单调递增；
  合并后的 `rec_893605581ba94ce9af1f`（合并 6 段）自动生成了一份覆盖整组的纪要「录音设备供电与参数调整」。

## 修复：语音转文字队列卡死（本地 sherpa-onnx native 死锁）
- 现象：71 个 transcribe job 卡 `running`、71 个 chunk 卡 `transcribing`，录音全部 `processing`，队列零进展。
- 诊断手法（很有用）：`sample <pid> 1 -mayDie` 看线程栈 → 8 个 job worker 全在
  `lock_PyThread_acquire_lock` + `__psynch_cvwait`，而 12 个 onnxruntime 线程全在
  `WorkerData::SetBlocked`（空闲）= 本地 ASR 在 native 层死锁，`_LOCAL_SEM` 被永久占住；
  `pg_stat_activity` 无锁等待，排除数据库问题；CPU 极低、无 ffmpeg 子进程。
  ⚠ 注意 `ps aux` 的 %CPU 是**进程生命周期平均值**，跑了几小时的进程永远显示 0.x%，
  判断瞬时负载要用 `top -l 2 -stats pid,cpu -pid X`。
- 根因：sherpa-onnx（Qwen3-ASR 0.6B int8）推理偶发 native 死锁；Python 无法杀掉卡在 C 扩展里的线程，
  重启服务后 2 分钟内必现。
- 修复（3 层）：
  1. `app/providers/local_asr_worker.py`（新）：常驻推理子进程，stdin/stdout 一行 JSON 协议，
     内部 `os.environ["LOCAL_ASR_ISOLATE"]="0"` 防递归。
  2. `app/providers/local_asr.py`：新增 `_LocalWorker` / `remote_transcribe()`，
     sherpa 与 faster-whisper 的 `transcribe()` 开头分流到子进程（whisper.cpp 本来就是子进程，不动）；
     超时 `max(180s, 时长*10+60)` → kill worker，下次调用自动重启（代价：重新加载模型）。
     另给 4 把锁换成 `_hold(lock, what)` 带超时（默认 300s，`LOCAL_ASR_LOCK_TIMEOUT`）。
     开关：`LOCAL_ASR_ISOLATE=0` 退回进程内推理。
  3. `app/jobs.py`：新增 `reap_stale()`（调度循环每 30s 跑一次）把 `started_at` 早于
     `JOB_STALE_SECONDS`（默认 600s）的 running job 重置为 pending，防止僵尸 running 永久堆积。
- 收尾：重启后端（8787，PID 65997）；两个"僵尸 transcribing"分片（job 已 failed 但分片没置 failed）
  手动重置 + 重新入队后转写成功；199 个分片全部 done，录音全部 ready。
  端到端验证：重跑一片 → job done，worker 子进程 66627 常驻。
- 坑：kill 主进程后 **旧进程可能没真死**（63846 仍在跑并 drain 同一个 jobs 表），
  重启后务必 `ps`/`lsof -iTCP:8787` 确认只有新进程在监听，必要时 `kill -9`。

## 队列加固：任务心跳 + PostgreSQL SKIP LOCKED
- 讨论结论：**不引入 RabbitMQ**。本次故障是推理层死锁，换 MQ 一样卡（还会变成 unacked 消息占死 prefetch，
  要等 `consumer_timeout` 才重投）。当前吞吐 <1 msg/s、单机部署，`jobs` 表 + 线程池足够。
- 迁移 `0005_job_heartbeat`：`jobs.heartbeat_at TEXT`，老数据用 `started_at` 回填。
- `app/db.py`：新增 `execute_returning()` —— 必须在同一个连接里 fetch RETURNING，
  因为 `execute()` 返回时连接已还池、cursor 失效（踩过的坑）。
- `app/jobs.py` 重构：
  - `_claim_one(type_)` 原子领取：PG 用 `UPDATE ... WHERE id=(SELECT ... ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING ...`，
    SQLite 去掉 `FOR UPDATE`。`drain()` 改为按 type 逐个领，天然遵守各类型并发上限。
  - 心跳线程 `_heartbeat_loop()`（默认 15s，`JOB_HEARTBEAT_SECONDS`）刷 `_in_flight` 里所有任务的 `heartbeat_at`。
  - `reap_stale()` 只按 `COALESCE(heartbeat_at, started_at)` 判活，`JOB_STALE_SECONDS` 默认 **600 → 120**。
    长任务只要心跳在跳就不会被误杀。
- 验证：
  - 10 线程并发抢 8 条 → 恰好 8 条唯一，无重复、无丢失（SKIP LOCKED 生效）。
  - 心跳：40s 慢任务 + `JOB_STALE_SECONDS=20` + 3s 心跳 → 全程 running 未被 reap，最后 done；
    伪造 heartbeat 落后 300s 的任务 → 被 reap 回 pending。
  - 生产端到端：新 job done，`heartbeat_at` 在任务执行中持续刷新。
- 环境：`LOCAL_ASR_ISOLATE` / `LOCAL_ASR_TIMEOUT` / `JOB_HEARTBEAT_SECONDS` / `JOB_STALE_SECONDS` 四个开关。
