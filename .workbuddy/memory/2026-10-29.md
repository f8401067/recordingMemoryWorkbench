# 2026-10-29 忆录（Recall Workbench）从零搭建

## 需求
录音笔类产品：网页/API 接收分段录音 → ASR 转文字 → 定时或手动整理成纪要 + 思维导图 → 日历查看每天记录 → 可自选 AI 服务商 → 漂亮响应式 Web。

## 技术选型（用户确认）
- 后端 Node.js 22 + TypeScript + Fastify 5（用户选 Node 而非 Spring Boot）
- SQLite（better-sqlite3，WAL），任务队列用 jobs 表 + 进程内 worker，不引 Redis
- 前端 React 18 + Vite + Tailwind 3，颜色用 `--*-rgb` 三元组变量以支持 `/opacity`
- ASR 默认 阿里百炼 Paraformer 实时（WebSocket 推本地 PCM，无需公网 URL）

## 关键实现
- `server/src/providers/asr.ts`：三种引擎（dashscope-paraformer 实时 WS / dashscope-qwen-asr 同步 base64 / openai-whisper 兼容）+ mock；统一 `AsrEngine` 接口
- `server/src/providers/llm.ts`：openai-compat / anthropic / mock，输出严格 JSON（title/markdown/mindmap/highlights/todos）
- 长文本纪要：>16000 字走 map-reduce（分段提炼 → 汇总）
- 录音切片：前端每 N 秒 stop+start 独立 MediaRecorder 实例，保证每片可独立解码（webm 分片不能直接切）
- 长音频上传：后端 ffmpeg `-f segment -c copy`，失败降级转 mp3 切片
- 思维导图：**弃用 markmap**（0.18 在本项目里节点宽度测量为 0，连线穿过文字），自研 SVG tidy-tree 布局，7KB chunk，支持缩放/拖拽/折叠

## 踩过的坑
- Fastify `addContentTypeParser('audio/*')` 不支持通配符，必须用正则 `/^audio\//`
- Tailwind `@apply placeholder:text-muted/70` 在颜色为 `var()` 时会报错，改为 rgb 三元组变量
- `stats` SQL 里 chunks 与 recordings 都有 `status` 列 → ambiguous column，必须加表别名
- Canvas `addColorStop` 不接受 `var(--brand)`，要先 getComputedStyle 解析
- 录音结束时 `rec.stop()` 是异步的，必须等 onstop 回调完成再判断分片数，否则会误判为「没录到内容」而删除记录
- ToastProvider 的 value 未 memo 会造成 context 变化 → useEffect 死循环 → 接口 500 时刷屏

## 验收
- Mock 全链路通过：建会话 → 分片上传 → 转写 → 纪要 → 导图 → 日历 → 日报 → 开放 API 同步转写
- 真实 ASR/LLM **未验证**（无 API Key），代码按官方协议实现，需用户配 key 后在设置页点「测试」
- 桌面 1440 / 移动 390 双尺寸截图确认，深色模式正常

## 运行
`npm run dev`（5173 前端 + 8787 后端）；生产 `npm run build && npm start`（单端口 8787）；`docker compose up -d --build`。
默认账号 admin / admin123，数据在 `data/`。

# 后端整体迁移到 Python（FastAPI）

## 结论
用户反馈「Python 的 AI 生态更丰富」，后端由 Node/Fastify 全量重写为 **FastAPI + uvicorn + uv**，
放在 `server-py/`；旧 Node 实现归档到 `legacy/nodejs-server/`（不再维护）。
**HTTP 契约、错误体 `{error}`、数据库表结构、`data/` 目录完全不变，前端零改动。**

## 目录
- `app/main.py` 入口（lifespan 里 init_db + 注册 job handler + 起 worker + 建初始账号；静态托管 + SPA 回退；异常处理器把 HTTPException 转成 `{error}`）
- `app/config.py`（`uid()` = 前缀 + 20 位 hex，与旧版一致）/ `db.py`（thread-local 连接 + WAL）/ `security.py`（bcrypt + PyJWT，`current_user` 依赖）
- `app/jobs.py` 表驱动队列（线程池 + `threading.Event` 唤醒），`app/bus.py` 进程内总线给 SSE
- `app/providers/{asr,llm}.py` 四类 ASR / 三类 LLM，与 TS 版一一对应
- `app/services/{transcribe,summarize,providers,settings,users}.py`
- `app/routes/{auth,recordings,summaries,providers,open}.py`

## 迁移要点 / 坑
- **时间字符串必须带 `Z`**：SQLite 里 `started_at` 是 `...T..:..:..mmmZ`，Python `isoformat()` 给的是 `+00:00`，
  按字符串比较时 `'+' < 'Z'` 会让边界日期漏掉 → 统一用 `strftime("%Y-%m-%dT%H:%M:%S.") + f"{us//1000:03d}Z"`。
- 本地日期（`local_date`/`day_range`）要按 **本地时区** 换算：`datetime.fromisoformat(...).astimezone()`，不能用 UTC。
- FastAPI 默认错误体是 `{detail}`，前端只认 `{error}` → 注册 `HTTPException`/`RequestValidationError` handler 转换。
- SSE 用 `StreamingResponse` + 轮询 `queue.get_nowait()`（`await asyncio.sleep(0.25)`），不能用阻塞 `q.get()`，否则卡住事件循环。
- 原生音频上传（开放 API）与 multipart 混在同一路由：用 `Request` 自己判断 `content-type`，不要用 FastAPI 的 `File` 参数。
- **修掉一个继承自 Node 版的老 bug**：`POST /recordings/{id}/retry` 原本无条件把 recording 置为 `processing`，
  没有待重试分片时会让记录永久卡在「转写中」→ 改成 `if not failed: return {"requeued": 0}`。
- 端口 8787 曾被旧的 Node 进程占用（`lsof -nP -iTCP:8787 -sTCP:LISTEN` 查 PID 后 kill）。

## 验收（全部通过）
`/tmp/flow.mjs`（建会话→分片→转写→纪要→导图→日历→日报→开放 API 同步转写）、
`/tmp/contract.mjs`（整段上传 ffmpeg 切片 4 片→回放→PATCH→服务商 CRUD→错误体→401→注册新用户）、
`/tmp/sse.mjs`（收到 ping/queued/transcribing/done/recording 共 5 条事件）、ego-browser 首页截图正常。
测试数据已清理，只留 admin 账号与两个 mock 服务商。

## 运行（新版）
`curl -LsSf https://astral.sh/uv/install.sh | sh` → `cd server-py && uv sync` → `uv run python -m app.main`；
或根目录 `npm run dev`（前端 5173 + 后端 8787）。Dockerfile 也改成 python:3.12-slim + uv。

# 硬件设备接入（ESP32-C3）+ 会话自动归并

## 需求
小硬件（ESP32-C3 一类）经网络推一段段音频；服务端要自己判断"哪几段属于同一次聊天"，
把时间相近的片段并成一条录音，再统一出纪要。

## 设计（设备极简，智能在服务端）
- 设备只需 `POST /api/open/ingest?device=<名>&key=<rk_>`，body 是音频二进制；**不用管会话、seq、时间偏移**。
- 服务端用**到达时间**判断边界（设备时钟不准也不影响）：
  - 距上一段 > `gapSec`(默认 90s) → 关掉旧会话、新建一条 recording
  - 静默 > `idleSec`(默认 180s) → 后台 sweeper（10s 一轮）自动收尾 → 触发自动纪要
- 新表 `devices`（user_id+name 唯一）：gap_sec / idle_sec / open_recording_id / last_chunk_at / session_chunks。
  `open_recording_id REFERENCES recordings(id) ON DELETE SET NULL`，删录音会自动断开指针。
- **关键**：`finalize_recording` 开头要判断「这条录音是不是还开着的设备会话」（查 devices.open_recording_id），
  是就直接 return。否则分片之间一有间隙就会被判定"全部转写完成"，一次聊天被拆成 N 条记录，还会生成半截纪要。
- 裸 PCM 支持：`audio/l16|pcm|raw` 服务端自动补 44 字节 WAV 头（`wrap_pcm_wav`），ESP32 端可以只推采样数据。
- 鉴权扩展：`X-API-Key` / `Authorization: Bearer rk_` / `?key=rk_`（单片机塞 URL 最省事）。

## 接口
| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/open/ingest` | 推一段，返回 chunkSeq / newSession / sessionDurationMs |
| GET | `/api/open/ingest?device=` | 设备自检 + 当前会话状态 |
| POST | `/api/open/ingest/close?device=` | 设备关机前主动收尾 |
| GET/PATCH/DELETE | `/api/devices[/{id}]` | JWT 后台管理（设置页「硬件设备」区块） |
| POST | `/api/devices/{id}/close` | 后台手动收尾 |

## 顺手修掉的 bug
`finalize_recording` 里调 `create_summary({...})` 是 TS 的对象参数写法，Python 版签名是 keyword-only，
**自动纪要一直在静默失败**（异常被 try/except 吞掉、print 又被管道缓冲看不到）。改成关键字调用后才正常。

## 验证
- 连续 3 段（间隔 0.8s）→ 同一条 recording，seq 0/1/2，累计 63s，转写完自动出纪要
- gapSec=3 + 静默 5.8s → newSession=true，旧会话 ready 且纪要 ready
- idleSec=10 → sweeper 自动收尾，录音 ready + 纪要 ready
- 裸 PCM 2s → durationMs=2000，WAV 头自动补
- 设置页设备区块桌面/390px 手机双尺寸截图正常；首页卡片显示「设备」来源标记
- 测试数据已清空，只剩 admin + 2 个 mock 服务商

# 硬件免登录配对：设备编号 + token（当天后续）

## 需求原话
「ESP32 没有键盘…硬件开机展示一个设备编号，是根据 MAC 换算的，固定。后台页面输入这个编号就完成绑定，
绑定后给设备发一个 token，后面设备每次发录音带着 token 就行。」

## 设计
- 设备编号 = MAC 后 4 字节 → 8 位大写十六进制（只用 0-9A-F，天然避开 O/I/L）。
- 服务端 `normalize_code()` 归一化：去分隔符、转大写、`O→0`、`I/L→1`，所以后台可以随便敲 `ab12 cd34`。
- 设备未持 token 时轮询 `GET|POST /api/open/pair?code=&name=&firmware=`：
  - 未绑 → `{"status":"pending","code":"...","pollAfterMs":3000}`，同时 upsert 到 `device_claims`
  - 已绑 → `{"status":"bound","token":"dv_..."}`（每次轮询都返回，便于换发 token 后自愈）
  - 按 IP 限速 60 次/分钟；编号格式非法直接 400。
- 后台（JWT）：`GET /api/devices/claims` 列 30 分钟内轮询过且未认领的编号；
  `POST /api/devices/bind {code,name?}` 生成 `dv_` + 40 hex token，之后从 claims 删除；
  同一编号被别人绑过 → `PermissionError` → 409「该设备已绑定到其他账号」。
- `POST /api/devices/{id}/reset-token` 换发，老 token 立即失效；设备下一次轮询自动拿到新的。
- 推流鉴权 `ingest_auth()`：先看 `X-Device-Token` / `Bearer dv_`，命中就按该 devices 行定位用户与设备；
  没有才回退账号级 `X-API-Key`。用 token 时 `device=` 参数被忽略，gap/idle 取该设备行配置。
- 表：`devices` 加 `code/token/bound_at/last_poll_at`；新表 `device_claims`（code 主键、poll_count、remote_ip、firmware）。

## 坑
- **partial unique index 不能写在 `schema.sql`**：老库 `CREATE TABLE IF NOT EXISTS` 不会补列，
  在 `schema.sql` 里 `CREATE UNIQUE INDEX ... ON devices(code)` 会直接 `no such column: code` 启动失败。
  → 索引统一挪到 `db._migrate()` 里、ALTER TABLE 之后再建（`WHERE code IS NOT NULL`）。
- 前端设置页的 claim 面板要 `Promise.all([devices, claims])`，否则绑定后提示条不消失。

## 验收
- 脚本 `/tmp/pair.mjs` `/tmp/pair2.mjs`：pending→claims 列表→用小写带连字符绑定→bound+token→两种 header 共用同一会话→错 token 401→reset 后老 token 失效→跨账号 409→非法编号 400。
- ego-browser 实测后台：点「添加设备」→ 输入 `9f3a-7c21` 自动变 `9F3A7C21` 并提示「将绑定为 9F3A-7C21」→ 提交后 toast「已绑定…」、蓝条消失、设备行出现；再推 2 片 4s，行内变「录音中 / 收尾 / 2 片」。
- 390px 手机视图无横向溢出（`scrollWidth == clientWidth == 390`），弹窗完整。
- 设备行补上 token 掩码显示（`dv_c05b...7335`），方便确认是否已下发。
- README 新增「① MAC→编号 ② 后台输编号 ③ 取 token 推流」三节 + 完整 Arduino 示例（含 401 自愈）+ 接口/参数表。

## 改版：编号从 8 位十六进制 → 6 位纯数字
用户理由：有些硬件连屏幕都没有，只能语音播报；6 位数字念起来/听起来都比带字母的十六进制简单。

- `CODE_RE = ^\d{6}$`；保留 `LEGACY_CODE_RE = ^[0-9A-F]{8}$`，老固件升级后仍能配对（判断顺序：6 位数字 → 纠错后 6 位 → 老 8 位）。
- 归一化升级：`normalize_code()` 先把**中文数字**（零〇洞一二两三四五六七八九幺）转成阿拉伯数字，再剔除非字母数字、转大写；
  只有 6 位校验失败时才应用 O→0 / I→1 / L→1 / Z→2 / S→5 / B→8 的纠错（否则会把老 8 位码里的 B 改掉）。
  所以 `903-471`、`903 471`、`九零三四七一`、`9O3471` 全部映射到 `903471`。
- 前端 `cleanCodeInput()` 做同样映射（含中文数字），`fmtCode()` 6 位显示成 `903-471`；输入框 placeholder `903471`、maxLength 8、inputMode numeric。
- 固件示例改为 `code = (x * 2654435761u) % 1000000u`，打散避免相邻 MAC 连号；补 `speakCode()` 逐位播报示例。
- 6 位数字共 100 万组合，撞号时后绑定方收到 409，删旧设备即可；已写进 README 说明。
- 实测：`12345` → 400「设备编号是 6 位数字，例如 903471」；中文数字可直接轮询/绑定；界面口述输入「五一八二零四」自动变 `518204` 并提示「将绑定为 518-204」。

## 撞号之争：加了 hwid 又撤掉（用户否决）
- 我提的担心：6 位数字只有 100 万空间，两台设备可能同号；先绑的那台占用编号后，第二台带同编号轮询会**静默拿到同一把 token**，录音混进第一台。
- 用户判断：不存在这个风险——绑定必须是「设备正显示编号 + 后台正开着绑定界面」同时成立的即时动作，撞不到。
- 于是把刚写好的 hwid 指纹校验整套回滚（schema 列、`normalize_hwid`、409 conflict、前端指纹与黄色警告条、README/界面示例），DB 里多出的列也用 `ALTER TABLE ... DROP COLUMN` 清掉了。**结论：方案保持简单，不引入 hwid。**
- 遗留事实（文档已按实测改准确）：若真出现同号且第一台已绑定，第二台轮询会拿到同一 token，后台显示的是先绑的那台；处理方式是删掉旧设备再绑新设备。README 不再写「后绑定方会收到 409」这种错话。

# 整理提示词升级：五套风格 + 用户自定义（2026-10-30）

## 改造前的问题
- 提示词写死在 `summarize.py`：一段 SYSTEM_PROMPT + 一段分段提炼 prompt。
- 设置里的「纪要风格」只是把标签塞进用户消息，**五套风格结构完全一样**（都是 会议结构）。
- `summaries` 表没有 template 字段，重新生成会退回默认风格。

## 现在的实现
- 新建 `app/services/prompts.py`：`STYLES` 每套含 `label / focus / outline / tips`，
  共用 `RULES`（只用原文、不编造、修同音错字、待办须有依据、只输出 JSON）和 `JSON_CONTRACT`（title/summary/markdown/mindmap/highlights/todos）。
  `build_system_prompt(template, custom)`：custom 非空时作为【用户自定义要求】替换风格描述，规则与 JSON 契约仍追加（否则前端解不出导图）。
  `build_chunk_prompt(template)`：map 阶段也带风格。
- `summaries.template` 落库（schema + `_migrate` ALTER）；`create_summary` 重新生成时「未指定则沿用原 template」；`public_summary` 返回 template。
- 设置新增 `summaryPrompt`（默认 ""），`PATCH /api/settings` 直接复用；`handle_summarize_job` 里 `read_settings()` 读取。
- 前端设置页「纪要风格」下加「自定义整理提示词（可选）」textarea + 保存 + 字数（2000 上限），dirty 才可点保存。
- MockLlm 会把命中的风格回显进标题和首段（"演示纪要 · 课程/讲座笔记"、"已应用你填写的自定义整理提示词"），方便确认链路。
